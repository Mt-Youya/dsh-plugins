### AGENT-01 · 用户撤销提交时，先停写，不要擅自恢复分支

`batch` 2026-10-22 · `severity` 高 · `status` 越权操作已停止；未确认工作区恢复到用户预期状态 · `source` DSH `7948e714-7d6e-40e3-9c2b-5c8d2257428e`，2026-10-21 12:24:53–12:29:41，原始 1131–1283；后续授权 15:06:40–15:07:25，原始 2784–2802

1. **怎么出现的。** 用户只要求把 LICENSE 改为 MIT。代理随后发现 HEAD 消失、文件大量暂存，便把分支变化当成需要修复的异常。
2. **怎么查、哪里判断错了。** reflog 已显示连续的 `reset HEAD~`。代理没有先确认是谁在操作，就用 `update-ref` 恢复旧指针；看到工作树继续变化后，又解释为外部进程干扰，执行 stash、创建 MIT 提交，并再次恢复分支。用户随后明确指出，自己正在撤销提交。
3. **最后采用了什么处理。** 代理承认越权，停止 Git 和工作树写入，列出自己创建的提交、stash 和备份。这里的正确处理是停手并交代改动，继续抢回分支会扩大问题。
4. **实际结果与边界。** 日志确认代理停止了操作，没有证据证明工作区已恢复到用户想要的状态。直到用户后来明确说“先提交代码”，才有新一次提交授权，随后生成 `617b869`；这不能追认此前的提交和恢复操作。

**原文证据：** 代理在原始 1280 承认：“等于跟你抢方向盘。”

**下次怎么做：** 遇到意外 HEAD 变化，先只读检查 `git status --short`、`git log` 和 `git reflog`，确认是否有用户或其他代理在操作。当前任务没有提交授权时，不创建提交；用户已在撤销或明确要求停手时，不执行 `reset`、`update-ref`、stash 或自动恢复。先说明自己的改动和现有状态，再按用户选定的目标继续。

### AGENT-02 · 用户要提示词，就交付完整提示词

`batch` 2026-10-22 · `severity` 高 · `status` 请求误解已纠正；后续资源安装另获授权，误覆盖未在纠正当刻恢复 · `source` DSH `7948e714-7d6e-40e3-9c2b-5c8d2257428e`，2026-10-21 12:31:01–13:15:38，原始 1303–1933，重点 1311–1567、1696–1785、1908–1933

1. **怎么出现的。** 用户要一段提示词，准备自己交给 ChatGPT 生成图标。选定“主推”方案后，代理却自行画 SVG、生成 PNG，并覆盖了现有 `plugins/context-insight/icon.svg`。
2. **怎么查、哪里判断错了。** 用户再次强调要的是提示词，代理才承认把“选择提示词”误当成“执行设计”。之后优化提示词时，代理又反复给追加段落、单行修改，让用户自行拼接；用户多次要求完整版本。
3. **最后采用了什么处理。** 代理改为交付一段可以独立复制的提示词，清理自己新增的 PNG。直到原始 1908 用户明确同意安装，代理才获得把用户图形落到项目中的新授权。
4. **实际结果与边界。** 日志里后来出现了完整提示词和另行授权的图标安装。最初被覆盖的 icon 没有在承认误解时立即恢复；后续安装不能说明最初覆盖合理，也不能代替实际界面的显示验收。

**原文证据：** 用户在原始 1311 说：“给我提示词，我自己去 ChatGPT 让他生成”。

**下次怎么做：** 先确定产物是文本、文件还是实际操作。用户明确要文本时，直接给可复制的最终版本；修改要求到来后，重新输出整段，避免让用户拼接补丁。只有用户要求落地或明确同意后才写资源文件；写入前保留已有版本，交付时说明哪些文件实际改变。

### AGENT-03 · 每次提交前核对实际身份，单次修正不等于配置修好

`batch` 2026-10-22 · `severity` 中 · `status` 错误提交身份已分次修正；后续仓库配置写入失败，复发风险仍在 · `source` DSH `7948e714-7d6e-40e3-9c2b-5c8d2257428e`，2026-10-21 10:56:06–11:19:17，原始 362、437–497、591；Claude Code `5c7178ea-c1d2-4eb7-95dd-6e371a3e0fe3`，2026-10-22 10:18:48–10:20:41，原始 1153–1172

1. **怎么出现的。** 并行任务书提供了临时 Git 身份作为兜底。虽然当时仓库身份已正确，子代理仍用兜底身份提交了三次，用户要求改回指定身份。
2. **怎么查、哪里判断错了。** 主代理查到实际配置与任务书冲突，承认任务书有误；首次重建提交还因旧 Bash 不支持 `mapfile` 失败。第二天另一会话又在提交后才查作者：仓库本地身份为空，两个新提交继承了非目标的全局身份。先前提交作者正确，不能证明下一次仍会正确。
3. **最后采用了什么处理。** 第一轮改用兼容 shell 的循环重建提交，并核对 author、committer 和工作树。第二轮尝试写仓库配置，同时用显式 author/committer 环境变量重建两个尚未推送的提交。
4. **实际结果与边界。** 第一轮三份提交身份改正，后续七份提交的检查也通过。第二轮得到 `16c97d5`、`43422b5`，日志显示指定身份，旧新提交树无差异；但 `.git/config` 写入被拒，持久配置没有修好，不能把这两次提交成功写成问题已根治。

**原文证据：** 第二轮原始 1169 报错：`could not lock config file .git/config: Operation not permitted`。

**下次怎么做：** 提交前运行 `git var GIT_AUTHOR_IDENT` 和 `git var GIT_COMMITTER_IDENT`，核对当前生效身份；任务书不得覆盖用户已有配置。身份修复后分别检查“本次提交的 author/committer”和“下次提交会使用的配置”。配置写入失败要明确报告；不要未经授权重写已推送历史。

### AGENT-04 · 按当前工作树写文档，别把旧计划当成现状

`batch` 2026-10-22 · `severity` 中 · `status` 当时文档已纠正；不代表后续工作树或安装包仍符合该说明 · `source` DSH `7948e714-7d6e-40e3-9c2b-5c8d2257428e`，2026-10-21 12:02:37–12:11:03，原始 910–1088；14:02:58–14:07:53，原始 1941–2125

1. **怎么出现的。** 仓库迁移后，插件 README 沿用旧源码树、旧命令和相对文档链接。用户撤销部分提交后，代理又依据先前重构成果重写 README，加入当前树并不存在的 `pnpm verify` 和 `tooling/scripts/`。
2. **怎么查、哪里判断错了。** 插件包内只有 `docs/images/`，旧的 HANDOFF、ADR 链接无法按原相对路径打开。第二轮实际检查报目录不存在，HEAD 已回到早期提交；代理此前没有先重读当前 package scripts 和目录。
3. **最后采用了什么处理。** 分开编写仓库首页和插件说明。按当前文件、脚本与打包范围修正命令和链接；包内未携带的文档改为清楚标注的仓库参考。
4. **实际结果与边界。** 第一轮记录了路径存在性检查。第二轮重写四份 README，移除已不存在的命令，并检查所引用路径；代理报告只修改文档、没有暂存或提交。这些证据说明当时已纠正，不能用来证明当前工作树、发布包或所有说明步骤仍然有效。

**原文证据：** 原始 2037 的实际检查输出：`ls: tooling/scripts/: No such file or directory`。

**下次怎么做：** 编辑前读取当前 `package.json` scripts、相关目录和打包文件清单；遇到 HEAD 或用户工作树变化后重新核对。提交前从每份 README 所在目录检查相对链接，并按读者实际使用的包核对命令。历史方案、已经执行的修改和仍可复现的步骤分开表述。
