### DEPLOY-01 · 包已装进依赖，不代表宿主能够识别并加载组合包

`batch` 2026-10-22 · `severity` 高 · `status` 声明已补，后续运行方案另有修订 · `source` claude-code 803d1bd2-861f-4b07-8abf-13e6a9d5868d，2026-10-21T09:41:37.377Z，原始行 906–1040；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-22T01:58:28.693Z，原始行 3199–3465

**1. 现象**：从 Git 安装工作区成功后，管理器仍提示“这个包没有声明组合包”；只 link 仓库根后，成员代码又未实际装入。

**2. 诊断**：原根包只有工作区元数据，缺少宿主使用的 `dsh.bundle.patch`。开发 workspace 的依赖解析、npm 发布转换与 profile 安装是三件事。尝试 bundleDependencies 又触发 `ERR_PNPM_BUNDLED_DEPENDENCIES_WITHOUT_HOISTED`。

**3. 方案**：先补 manifest、patch、locale 与发布声明，使用 `workspace:^`，按当时选择先发布成员再发布根包；没有为一次试验将全仓改为 hoisted。后来为了本地 UI 添加根包，又演进为根包自带运行入口，不能把两阶段说明混写。

**4. 实现与验证**：早期 tarball 中依赖转换为 `^0.0.2` 有证据；后续根入口、profile 路径和 hash 也有检查。但末尾只交还用户手动添加步骤，后续仍有 renderer 失败，不能称 npm 发布或桌面集成已闭合。

**预防**：先明确当前支持的安装产物，再核对 tarball 的 manifest、patch、exports 和实际入口。不要把旧发布方式的要求直接当作新本地加载方案的验收结论。

### DEPLOY-02 · 宿主按根包名等待 factory，成员 ID 会触发重复执行

`batch` 2026-10-22 · `severity` 高 · `status` 身份与产物检查通过，冷启动前端待验收 · `source` dsh da47cfd3-4e86-4cbd-9d97-a079a6d1ac5a，2026-10-22T02:57:52.156Z，原始行 267–645；claude-code 117bc152-78c4-49a0-bd41-9762cc6a3110，2026-10-22T02:59:00.461Z，原始行 108–359

**1. 现象**：桌面日志同时出现根包 `import failed` 和成员 factory 重复注册。

> `duplicate factory registration for "@cyrus/dsh-context-insight"`

**2. 诊断**：根包 exports 复用成员 client 字节，banner 却固定注册成员 ID。宿主按根包名等待 factory，首次执行后仍认为根模块没注册，fallback 再执行同一产物便撞重复 factory。隔离 Host health 200 没有加载前端，不能推翻这条客户端证据；“旧 HMR”当时只是推断。

**3. 方案**：banner 从被构建包的 `manifest.name` 派生；根与成员分别生成自己的 lib；打包校验也读取被检 manifest，而不是硬编码唯一名字。

**4. 实现与验证**：两份 banner 分别为自身 ID，两份 bundle 校验、profile 实际解析路径与 hash 通过。记录没有最终浏览器冷启动成功。服务端 duplicate route 的残留清理是另一问题，见 [DATA-04](./02-ui-and-host-contracts.md#data-04)，不合并成已确认同根因。

**预防**：同时核对安装包名、loader entry、client 注册 ID 和 exports。Host 与 renderer 各自复现；不要因二者都带 duplicate 就直接归为双进程或同一次加载。

### DEPLOY-03 · 安装命令成功后，profile 里仍可能是旧字节

`batch` 2026-10-22 · `severity` 高 · `status` 历史已回读字节，整体运行仍待验收 · `source` dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T06:21:31.292Z，原始行 2498–2513；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T06:32:31.313Z，原始行 2674–2690；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T08:39:16.201Z，原始行 3138–3180

**1. 现象**：`dsh plugin add` 成功，新构建 marker 在已安装包中却命中 0，文件时间也没变；加 `--force` 后仍复发。

**2. 诊断**：同版本、同路径 file tarball 的缓存使旧副本被继续使用。安装器的成功状态只证明命令结束，没有证明更新字节已经落入运行 profile。

**3. 方案**：历史比较构建与安装的 client hash，并定点回读 marker；发现旧副本后重新解包。后来的安装脚本加入版本、路径和 hash 核对。

**4. 实现与验证**：后续 marker 命中、两次脚本运行的 client hash 一致有记录。但仅核对 client 不覆盖 host-only 改动，部分命令还用 `|| true` 吞错；不能将这些证据扩成 profile 注册和桌面重启都成功。

**预防**：安装后核对实际解析路径、版本和本次改动涉及的产物 hash；涉及 host 时也核对 host。给缓存键或产物命名足够区分度，再做目标进程加载验证。

### DEPLOY-04 · tarball 版本名写死，再继续删除会把可用安装变成空目录

`batch` 2026-10-22 · `severity` 高 · `status` 历史副本恢复，失败顺序需持续守护 · `source` dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T07:36:47.949Z，原始行 2991–3021；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T08:39:16.201Z，原始行 3138–3180

**1. 现象**：打包已产出 0.0.2，安装命令仍复制 0.0.1；后续检查发现已安装目录没有 `client.js`。

**2. 诊断**：脚本处于 `set +e`，旧文件复制失败后继续删除安装目录、创建目录并解包。前面的构建和单测通过，无法保护这个独立的安装顺序错误。

后续回读确认：已安装目录缺少 `client.js`。

**3. 方案**：先定位实际 0.0.2 tarball 并重新解包；随后脚本动态选择产物并启用失败即停。历史手动删除属于当时操作证据，不是建议读者照做的修复命令。

**4. 实现与验证**：正确副本的版本、locale、hook 和 client hash 后来恢复。完整宿主仍需独立验证；错误吞掉、仅比较 client 等限制见 [DEPLOY-03](#deploy-03)。

**预防**：替换前确认候选产物存在、可解包且入口完整；在临时目录校验后再交换，任何准备步骤失败都保留现有可用副本。

### DEPLOY-05 · 管理器 icon.svg 与侧栏图标可能是两个独立入口

`batch` 2026-10-22 · `severity` 中 · `status` 实际组件已更新，宿主视觉待验收 · `source` dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T05:15:24.133Z，原始行 1911–1933；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T06:09:37.919Z，原始行 2134–2177

**1. 现象**：代理已经报告图标装好，用户的真实侧栏截图仍显示旧图形。

**2. 诊断**：manifest 的 `icon.svg` 用在插件管理卡片；侧栏注册另有 `client/index.tsx` 中的 `ContextInsightPanelIcon`，仍硬编码旧 path。只改资源文件不会改变该组件。

**3. 方案**：从用户实际看到的槽位反查渲染入口，更新内联图标组件；不再凭文件名推断所有位置共用同一资源。

**4. 实现与验证**：历史构建、测试通过；tarball 中新 path 命中 1、旧 path 命中 0，证明包内字节已变。未记录桌面重启后的用户视觉确认，不能把字节检查写成实际显示已验收。

**预防**：列出每个使用位置和入口，沿注册与组件调用链核对；分别验证管理器、侧栏和 README 的资源消费。
