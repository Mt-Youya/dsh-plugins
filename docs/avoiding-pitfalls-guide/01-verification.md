### VER-01 · 尾命令的退出码会把测试失败包装成成功

`batch` 2026-10-22 · `severity` 高 · `status` 历史复验通过，旧结果失效 · `source` dsh 1cf5a307-66d7-41fd-9d79-932cf9933dd0，2026-10-21T03:49:35.989Z，原始行 294–347；dsh 1cf5a307-66d7-41fd-9d79-932cf9933dd0，2026-10-21T03:55:00.023Z，原始行 544；dsh 33266fec-3179-4d0b-b369-19c5912d4d13，2026-10-21T03:37:48.060Z，原始行 282–315；codex 01a15cc1-8162-7093-a37c-230bc6893307，2026-10-21T05:09:31.620Z，原始行 269–279

**1. 现象**：测试拆分后，终端显示 `exit=0`，Vitest JSON 却是 56 通过、11 失败。图标像素检查也出现 `AssertionError`，整个 Shell 命令仍退出 0。

**2. 诊断**：前者把测试接到 `tail`，取到的是尾进程状态；后者在 Python 后另跑成功的 `git diff --check`，覆盖了前面的失败。正文里的错误与退出码不一致，说明驱动脚本本身有问题。

> `ReferenceError: at is not defined`

**3. 方案**：分别保存原命令日志和退出码；管道启用失败传播。测试还要读实际汇总，不能只认封装返回的 0。预期失败的负例按 [VER-07](#ver-07) 单独捕获。

**4. 实现与验证**：补齐 helper 后，测试 JSON 变为 67 通过、0 失败；拆分界面的两套类型检查改为直接运行后退出 0。图标验证随后独立运行通过，并将已出现的像素主色与明确的 1/255 容差分开检查。不能拿后来成功替早先假绿背书。

**预防**：先用一个确定失败的输入验证驱动会返回非零；检查失败正文、实际断言汇总和原进程状态三者是否一致。

### VER-02 · 比较器没读取文件，增加样本也只是在比较空输出

`batch` 2026-10-22 · `severity` 高 · `status` 等价性待有效重验 · `source` dsh ae5c4a70-e3ba-4628-a743-bf17bc9bfa52，2026-10-21T03:50:15.454Z，原始行 298–305；dsh ae5c4a70-e3ba-4628-a743-bf17bc9bfa52，2026-10-21T03:55:19.708Z，原始行 481–518；dsh ae5c4a70-e3ba-4628-a743-bf17bc9bfa52，2026-10-21T04:01:12.882Z，原始行 641–758；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T04:03:22.984Z，原始行 946–1018

**1. 现象**：探针拆分报告“11/11 一致”，同一批原始输出却先报失败，再报比较通过。

> `FAIL-corpus` / `FAIL-small`，随后 `OK codex-corpus` / `OK codex-corpus-small`

**2. 诊断**：历史 `normalize.sh` 只有 `sed -E` 及若干 `-e`，结尾没有 `"$@"`；调用方式却是 `./normalize.sh <文件路径>`，没有把文件重定向到 stdin。由脚本文本与调用方式可推得：在当时空 stdin 下，两侧归一化都为空。与此同时业务探针的 `percent` 未导入，失败也被“相同”掩盖。

**3. 方案**：历史只修残余 `percent` 引用，后续冻结 HOME、加 A/B/A、比较 stderr 与退出码时，仍沿用同一个比较器；主代理采信了交付摘要，没有独立修正这一点。

**4. 实现与验证**：业务引用修正有记录，比较器本身未见修复或正确复验。增加样本和冻结输入不补偿比较器读空。这里的缺陷来自本次对脚本、参数和相邻结果的审阅，未执行历史脚本，也不将后来普通门禁当作等价证明。

**预防**：先给比较器两份已知不同的非空文件，检查输入数量、归一化字节数和失败状态；再用同一份冻结语料跑前后版本。stdout、stderr、退出码分别比较，不能把退出码也送入忽略文件参数的过滤器。

### VER-03 · 零失败可能只是发现规则没有命中任何语料

`batch` 2026-10-22 · `severity` 中 · `status` 夹具已调整，等价结论仍受限 · `source` dsh ae5c4a70-e3ba-4628-a743-bf17bc9bfa52，2026-10-21T03:45:44.731Z，原始行 164–221；dsh ae5c4a70-e3ba-4628-a743-bf17bc9bfa52，2026-10-21T03:49:25.091Z，原始行 276–293；dsh 6ea98f37-0a86-4e98-a254-47105788aea8，2026-10-21T03:40:08.297Z，原始行 1812–1869

**1. 现象**：小语料测试打印 `rollout files 0`、`parsed 0/0`、`failures 0`。另一次打包检查没找到 tgz，仍打印“0 bare internal imports”。

**2. 诊断**：夹具把 Codex 文件改成 `a.jsonl.zst`、`b.jsonl.zst`，发现器只接受 `rollout-` 前缀；打包检查则在错误目录找文件。空结果分别来自被过滤和输入不存在，均未执行所声称的检查。

**3. 方案**：夹具保留原文件名；先定位真正 tarball 再解包检查。另有 DSH 默认样本在模块顶层 eager stat，历史用补齐 fake HOME 默认路径绕过；它没有修复这项既有前置依赖。

**4. 实现与验证**：重建夹具后对应模式能够运行；真正解包后才有包内依赖、loader ID 与 scope 检查。探针前后等价仍受 [VER-02](#ver-02) 影响，不能补写成已通过。

**预防**：检查前明确预期的非零文件数、解析数、轮次数和输入摘要；找不到输入必须失败，禁止无条件打印成功文字。

### VER-04 · 字符串指纹相同，只能证明它实际统计的那些字符串

`batch` 2026-10-22 · `severity` 中 · `status` 验证范围已限定 · `source` dsh 33266fec-3179-4d0b-b369-19c5912d4d13，2026-10-21T03:37:27.989Z，原始行 267–277；dsh 33266fec-3179-4d0b-b369-19c5912d4d13，2026-10-21T03:39:10.317Z，原始行 357–405

**1. 现象**：界面拆分以 96 条标记一致宣称“逐行一致”，但包含性检查实际少了 25 行，其中有回调改走 props 等结构变化。

**2. 诊断**：指纹统计 className、data-part、翻译调用的字符串多重集。它看不到 DOM 父子关系、回调参数、状态迁移和滚动边界；同一组字符串可以组成不同界面。

历史差异检查保留了 `25` 行差异，不能被“指纹一致”抹掉。

**3. 方案**：解释预期结构改动，补产物 className 检查和真实 Chrome 双主题冒烟；不为每个搬运符号另造测试。

**4. 实现与验证**：历史冒烟确实覆盖挂载、至少三行、边框、输入字号、来源标签颜色，五道门禁随后通过。它们支持“所列检查通过”，不支持“全部 DOM 与交互行为等价”；记录中也未证明存在具体交互回归。

**预防**：为每个检查列出可见范围；若变动了事件或布局边界，直接检查该行为，避免把内容指纹升级为全部行为保证。

### VER-05 · 图标长度必须说明是否包含圆帽，再检查小尺寸形态

`batch` 2026-10-22 · `severity` 中 · `status` 数值方案已确认，历史审图误判另记 · `source` codex 01a15cc1-8162-7093-a37c-230bc6893307，2026-10-21T04:59:58.465Z，原始行 178–204；codex 01a15cc1-8162-7093-a37c-230bc6893307，2026-10-21T05:05:35.153Z，原始行 211–284；dsh 7948e714-7d6e-40e3-9c2b-5c8d2257428e，2026-10-21T04:55:49.276Z，原始行 1747–1901

**1. 现象**：图标通过 52% 镜片、20%／14%／8% 横条的数值检查后，用户仍要求最短条清楚呈现横条，而不是接近圆点。

**2. 诊断**：若 8% 是含圆帽总长，粗细 7% 时长宽比只有 1.14。另一个 DSH 会话只算路径端点差，把原本含圆帽正确的 23% 或 20% 判成偏短。这一误判是本次从 SVG 推导的审阅结论，历史代理没有自行确认。

> `visibleBarPercent:[27,21.000000000000004,15.000000000000002]`

**3. 方案**：用户明确选择 56% 镜片，20%／14%／8% 改指中心线路径长度，圆帽另计。圆帽直线可见长度为路径长度加描边宽度；外圆直径也要含描边。

**4. 实现与验证**：Codex 从实际 SVG 提取坐标，核对间距、圆内间隙、边界与透明像素，最短条可见长度约为最长的 56%，长宽比约 2.14。保留了历史预览调用，但本轮没有重看图片，不能另称已完成视觉验收。早期硬编码期望数值的断言也不能独立证明当时 SVG 全部正确。

**预防**：先固定中心线、可见边界和像素三种口径；断言读取实际产物，最终在目标 12／16 px 尺寸观察形态。不得为了让数字过关擅改用户已选口径。

### VER-07 · 负例正确失败后，驱动脚本仍必须完成清理

`batch` 2026-10-22 · `severity` 中 · `status` 历史正反例已复验 · `source` dsh b377c656-f60c-48ff-95ca-fe12d7802c6a，2026-10-21T03:58:52.673Z，原始行 589–649；dsh b377c656-f60c-48ff-95ca-fe12d7802c6a，2026-10-21T04:01:34.089Z，原始行 698

**1. 现象**：用 501 行文件反证行数守卫，命令在命中违规后直接结束，后面的删除步骤没有执行。

**2. 诊断**：测试驱动启用了 `set -eu`，预期的守卫 exit 1 先终止了驱动，尚未记录状态，也没撤销夹具。守卫本身正确，驱动清理却失败。

**3. 方案**：显式捕获预期失败，清理夹具后再断言退出码；对非预期中断也安排清理。不要用永远成功的 `|| true` 抹掉负例断言。

**4. 实现与验证**：后续记录了行数基线 0、注入 501 行后 1、撤回后 0；两个依赖边界违规也分别为 1、撤回为 0。最后历史 verify 退出 0、182 项测试通过。

**预防**：负例同时验收“检测到了违规”和“测试结束后回到基线”；共享树里的临时文件需有明确责任人与退出清理。
