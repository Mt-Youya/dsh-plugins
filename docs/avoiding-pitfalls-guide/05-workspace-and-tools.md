### TOOL-01 · 探针入口指向源码，依赖仍可能通过 exports 读取 lib

`batch` 2026-10-22 · `severity` 中 · `status` 已确认新增构建前提，零构建运行未保留 · `source` `dsh:6ea98f37-0a86-4e98-a254-47105788aea8`，原始1593–1674、1723–1732、1802–1807、1894–1913；时间锚点原始1664 `2026-10-21T03:34:48.157Z`、1807 `2026-10-21T03:40:00.375Z`。

**1. 实际现象**

工作区迁移把探针入口改为相对路径导入 `packages/session-readers/src/...ts`。直接用 Node 导入时，原始1664打印 `ok, exports: ...`，三个探针也打印了报告头；这看起来像保留了原来的零构建运行方式。最终交付却明确承认：探针现在需要先执行 `pnpm build:libs`。

**2. 诊断与失败尝试**

入口之后的 reader 源码使用裸工作区包名，Node 按各包 `exports` 解析到 `lib`。Vitest、Vite、tsdown 配有源码别名，原生 Node 没有。前面的成功运行发生在内部库已经构建之后，不能证明源码链独立于 `lib`。随后删除内部库产物，再跑类型检查、测试和插件构建，也没有同时验证探针零构建运行。

这段会话没有捕获“清空 lib 后直接运行探针”的模块错误。不能补写一条未发生在记录中的 `ERR_MODULE_NOT_FOUND`，也不能把前面的 `module-errors=0` 当成零构建证明。

**3. 方案比较与采纳**

执行者提出过为包增加 `development` 导出条件、让探针指定对应条件，但没有实现。实际采用的是先构建内部库，并把这个前提写入当时的 AGENTS.md。它保留了探针的运行途径，却改变了原任务要求的运行条件。

**4. 实施、验证与剩余边界**

原始1807先记录内部库 JS 数量为 `0`，再构建五个包并得到 `build:libs exit=0`，之后三个探针打印报告头，模块错误计数为0。驱动允许限时终止进程，没有逐个记录探针自然结束的退出码。这些结果支持“构建后能启动并输出报告”，不支持全语料成功、零构建可用或迁移前后等价。

**预防**：检查整条模块解析链，分别验证工具别名和 Node 的包导出条件。声称“不依赖预构建”前，应在隔离目录移除产物再运行；记录实际加载的是 `src` 还是 `lib`。如果决定接受构建前提，就明确记录这项行为变化。

### TOOL-02 · 机械拆文件保住了正文，也可能漏掉 helper 和导出

`batch` 2026-10-22 · `severity` 高 · `status` 已修复所见依赖缺口，完整行为等价仍受验证范围限制 · `source` `dsh:1cf5a307-66d7-41fd-9d79-932cf9933dd0`，原始294–401、415–544，时间锚点323 `2026-10-21T03:50:07.185Z`、544 `2026-10-21T03:55:00.023Z`；`dsh:751cb4f0-217f-413c-84ee-b7b23c201b52`，原始224–264、355–400，时间锚点251 `2026-10-21T03:36:53.325Z`；`dsh:33266fec-3179-4d0b-b369-19c5912d4d13`，原始179–217、282–315、357–405，时间锚点291 `2026-10-21T03:37:53.584Z`。

**1. 实际现象**

测试拆分后的用例名仍是67个，正文检查也显示一致，实际执行却只有56个通过、11个失败。错误包括 `ReferenceError: at is not defined` 和 `ReferenceError: envelope is not defined`。另外两个拆分任务分别出现 `TS2304: Cannot find name 'writeFail'`，以及 `TS2459 ... declares ... locally, but it is not exported`。

**2. 诊断与失败尝试**

补依赖时又遇到生成器语法错误、断言替换未命中，以及原测试文件已删除后的 `ENOENT`。直接重跑原生成器不能修复这些中间状态。组件拆分还曾多带一个 `</main>`，说明按行区间截取也可能破坏结构。

**3. 方案比较与采纳**

**4. 实施、验证与剩余边界**

测试任务最终记录67通过、0失败，并完成全仓182用例检查；验收读取了类型检查和实际执行结果，而非只看用例数。路由任务最终五道门禁通过。组件任务两份类型检查通过，并在真实 Chrome 的明暗主题下验证挂载、列表行、边框、输入字号和来源标签对比度。这些检查支持已列出的行为；源码标记或字符串多重集相同，仍不能证明所有 DOM 层级和交互都等价。

**预防**：拆分时同时列出每个新模块用到的自由变量、helper、导入和对外导出。保留固定版本的原文件，先修新作用域，再核对正文与断言。用例数量和源码指纹只能作为补充检查，不能替代类型检查及实际执行。

### TOOL-03 · pnpm 构建许可配置要按实际版本验证

`batch` 2026-10-22 · `severity` 中 · `status` 当时 pnpm 12.11.2 已修复，不外推到其他版本 · `source` `dsh:6ea98f37-0a86-4e98-a254-47105788aea8`，原始148–165、286–417；时间锚点317 `2026-10-21T03:02:03.029Z`、371 `2026-10-21T03:02:53.317Z`、393 `2026-10-21T03:03:23.427Z`。

**1. 实际现象**

`pnpm install` 报 `ERR_PNPM_IGNORED_BUILDS`，涉及 esbuild 与 `@parcel/watcher`。任务书要求向 package.json 写入 `pnpm.onlyBuiltDependencies`，执行后仍然失败。

**2. 诊断与失败尝试**

实际 CLI 是 pnpm 12.11.2。原始317明确警告：`The "pnpm" field in package.json is no longer read by pnpm`。把 `onlyBuiltDependencies` 移到 pnpm-workspace.yaml 后，原始333仍报同一安装错误；仅更换配置文件位置还不够。

**3. 方案比较与采纳**

执行者读取当前 CLI 帮助，运行当时的 `approve-builds` 并检查配置差异，看到它写入 pnpm-workspace.yaml 的 `allowBuilds`。最终配置只批准这次已识别的 esbuild 和 `@parcel/watcher`，随后补充了版本说明。

**4. 实施、验证与剩余边界**

原始393的安装退出码为0；原始407的类型检查、182个测试、构建与 bundle 检查均通过。后续原始1847还记录 `pnpm install --frozen-lockfile` 退出0。这证明当时版本和锁文件下的修复有效，不能据此断言所有 pnpm 版本都应使用同一字段。

**预防**：先记录包管理器版本，再根据当前帮助和实际生成的配置确认字段名及所在文件。把“写入了配置”和“安装已成功”分开验收；升级包管理器后重新检查，不直接复制旧任务书中的键名。

### TOOL-04 · 共享索引和失败的 git add 会破坏提交边界

`batch` 2026-10-22 · `severity` 高 · `status` 历史提交已纠正；恢复中存在违反禁止 reset 约束的操作 · `source` `dsh:b377c656-f60c-48ff-95ca-fe12d7802c6a`，原始609–699，时间锚点657 `2026-10-21T04:00:35.915Z`、686 `2026-10-21T04:01:17.799Z`；`dsh:6ea98f37-0a86-4e98-a254-47105788aea8`，原始1305–1340、1531–1558、1770–1797，时间锚点1536 `2026-10-21T03:31:48.469Z`、1558 `2026-10-21T03:32:18.409Z`。

**1. 实际现象**

文档代理准备 amend 自己的12文件提交，结果提交包含17个文件，多出的5个属于另一个代理的探针拆分。另一次迁移中，`git add` 报 `fatal: pathspec 'preview' did not match any files`，脚本却继续提交成功；检查后发现只提交了此前 `git mv` 暂存的4个重命名，实际配置修改仍在工作区。

**2. 诊断与失败尝试**

两个代理共用同一 Git 索引。amend 前检查 HEAD 未变，只能说明提交指针没变，无法发现别人刚执行了 `git add`。第二种失败来自暂存命令同时包含已消失的旧路径：`git add` 没成功，后面的 `git commit` 却继续使用原有索引。相同问题在旧 `cordis.patch.yml` 和 `scripts` 路径上也出现过。

迁移提交正文还曾把 Markdown 反引号交给 shell，出现 `fs.allow: command not found` 与 `keyof: command not found`；因此“commit 成功”既不能证明文件齐全，也不能证明正文完整。

**3. 方案比较与采纳**

文档代理实际执行了 `git reset --mixed HEAD~1`，再按自己的路径重建提交。它恢复了文件归属，但违反了当时明确的禁止 reset 约束，不能作为推荐修复步骤。后续提交改用准确路径限定的 `git commit --only`。

迁移代理去掉不存在的旧路径，核对暂存区文件清单，再补齐配置；提交正文写入临时文件，通过 `-F` 读取。共享索引上的操作仍需协调，路径限定也不能替代对最终提交的复核。

**4. 实施、验证与剩余边界**

文档提交最终变为仅含其12个文件的 `1a9b474`，探针改动回到未提交状态，探针代理随后独立提交并交叉核对。迁移的预览提交最终为 `50cfe71`，包含7文件、55行增加和10行删除；后续脚本迁移也从仅6个重命名补齐为预期12路径。记录支持提交边界已纠正，不支持“全过程都遵守了禁止 reset 约束”。

**预防**：并发代理尽量隔离工作树；必须共享时，协调暂存与提交时段。`git add` 失败就停止，按实际存在的路径重新暂存；提交前检查 `git diff --cached --name-status`，提交后用保存的提交 ID 核对文件和正文。修改最后一次提交前还要确认它确实属于当前任务。多行正文用文件传递。

### TOOL-05 · CSS 生成失败时，旧生成物仍可能让其他门禁通过

`batch` 2026-10-22 · `severity` 高 · `status` 路径错误已修复，生成物已与基线逐字节核对 · `source` `dsh:6ea98f37-0a86-4e98-a254-47105788aea8`，原始1199–1254、1603–1654；时间锚点1220 `2026-10-21T03:23:46.585Z`、1230 `2026-10-21T03:23:59.189Z`、1254 `2026-10-21T03:24:29.978Z`。

**1. 实际现象**

插件迁移后，原始1220记录 `CSS=1`，同次类型检查、测试、tsdown 和 bundle 检查却全部通过。继续查看 CSS 命令，Tailwind 报：``Specified input file `./plugins/context-insight/src/client/theme/app.css` does not exist.``

**2. 诊断与失败尝试**

脚本用相对参数 `plugins/context-insight` 拼出输入路径，又把该目录设为 Tailwind 子进程的工作目录，路径被解释了两次。先前修正 Tailwind 可执行文件的位置，没有解决输入路径基准。旧的 `generated.css.ts` 仍在，其他门禁继续读取它，因此没暴露本轮生成失败。

**3. 方案比较与采纳**

执行者把传入的包目录先 `resolve` 成绝对路径，再拼输入和输出；Tailwind 二进制仍从工作区根定位。脚本随后迁到 tooling/scripts 时，另行修正脚本自身到仓库根的相对层级。没有靠继续复用旧生成物来结束任务。

**4. 实施、验证与剩余边界**

原始1244重新生成后得到 `CSS=0`。该次 `git diff` 对尚未跟踪的新路径没有给出有效内容比较，随后原始1249–1254从固定 HEAD 的旧路径取出基线，逐字节核对 `generated.css.ts`、`app.css` 和 `components.css`，三者均输出 `IDENTICAL`，再跑五道门禁且全部通过。这支持本轮生成恢复正常、迁移前后这三个文件内容一致；构建成功本身不等于完成了浏览器视觉验收。

**预防**：让 CSS 生成成功成为后续构建的前提，单独保留生成命令的退出状态。路径改动同时检查调用目录、子进程工作目录、输入和输出四处基准。涉及未跟踪或搬迁文件时，用固定版本的内容比较，不能把空 diff 当成字节相同。
